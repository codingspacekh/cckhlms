## Question
Can Better Auth provide username + password login, Admin-created accounts only, **different session lengths for students and staff** (students 2 h idle / 12 h max on shared laptops; staff 7 days rolling), "sign out everywhere" and login rate limiting, with Drizzle + PostgreSQL?

## What was built
- `better-auth@1.7.7` with the **username** and **admin** plugins, Drizzle adapter, PostgreSQL 18 (Docker). Tables follow `getAuthTables()` for this plugin set, with snake_case columns and a `last_active_at` session field.
- `emailAndPassword.disableSignUp = true`. Accounts are created by Admin (`/admin/create-user`); the first admin is seeded with `internalAdapter.createUser` + `linkAccount`.
- **Session rules in our code:**
  - Better Auth keeps one outer limit (7 days, refreshed daily).
  - `getActor(headers)` is the only way server code learns who is calling. It applies `sessionDecision()`: students are signed out after 2 h idle or 12 h total, staff after 7 days idle or 30 days total. It deletes expired sessions and records activity at most once a minute.
- **Rate limit:** 5 sign-in attempts per minute per IP on `/sign-in/username`, stored in the database. The IP comes from Cloudflare's `cf-connecting-ip` header.
- **Origin hook** (`hooks.before`): every browser POST to `/api/auth/*` must carry `Origin: <LMS>`.

**Versions (exact):** `better-auth@1.7.7`, `drizzle-orm@0.45.3`, `pg@8.23.1`, `postgres:18-alpine`.

## Findings
1. **Per-role session lengths aren't built in.** Better Auth has one global `expiresIn`/`updateAge`, and its refresh resets expiry to `now + expiresIn` for everyone.
   **Decision:** keep Better Auth's limit as the outer bound and enforce the role rules in `getActor()`, which every server action and route already calls for authorisation (ADR-10). Tested above.
2. **Sign-in has no CSRF check without a cookie.** Better Auth validates `Origin` only when the request already carries a cookie. The "first login" Fetch-Metadata check exists but is attached to some endpoints and **not** to the username plugin's `/sign-in/username`. A hostile page (or a student preview) could therefore sign a student into another account ("login CSRF").
   **Decision:** a `hooks.before` middleware rejects any browser POST to `/api/auth/*` whose `Origin` isn't the LMS. Server-side calls are unaffected. Re-check this whenever Better Auth is upgraded (the test stays in the suite).
3. **Email is required by the core user table.** Accounts get a non-routable placeholder `username@users.cckh.invalid`. No email is ever sent (none is configured), and the address is never shown.
4. **Rate limiting needs the real client IP.** Behind Cloudflare that is `cf-connecting-ip`. Configured via `advanced.ipAddress.ipAddressHeaders`; database storage keeps limits across restarts. The Cloudflare rule on `/api/auth/*` stays as the outer layer.
5. **`disableSignUp` doesn't block Admin creation** (`/admin/create-user` works), and a non-admin gets 403. That's the behaviour we need.

## Decision
**GO** with Better Auth (username + admin plugins), plus our origin hook and `getActor()` session rules.

## Consequences for M1/M2
- M1: move `auth.ts`, `actor.ts`, `session-policy.ts` and their tests into the app; the Policy matrix harness builds on `getActor()`.
- M2: Admin account screens use `/admin/create-user`, `/admin/set-user-password` and `/admin/revoke-user-sessions`; usernames are validated in our Zod schemas (3–30 chars, letters, digits, `.` and `_`).
- Upgrades: the origin and session tests are the guard. If Better Auth adds per-role sessions or fixes the username CSRF gap, we can simplify, but only with those tests still green.
